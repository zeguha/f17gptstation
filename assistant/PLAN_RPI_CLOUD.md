## Цель

Сделать «почти идеального» голосового ассистента для Raspberry Pi с wake «олег», который:

- устойчиво срабатывает в реальных условиях (шум, быстрые реплики, паузы);
- отвечает голосом на русском;
- использует облако для качества (ASR/LLM/TTS), но сохраняет локальный контур устойчивости (аудио, VAD, wake, запись, state-machine);
- остаётся модульным: можно менять провайдеров без переписывания пайплайна.

База, от которой отталкиваемся: текущий репозиторий с пайплайном wake/команда и cloud-эн트рипоинтом (см. [`assistant/main_cloud.py`](assistant/main_cloud.py:1), [`assistant/pipeline_vosk.py`](assistant/pipeline_vosk.py:1), [`assistant/cloud_interfaces.py`](assistant/cloud_interfaces.py:1), [`assistant/cloud_openai.py`](assistant/cloud_openai.py:1), [`assistant/config.py`](assistant/config.py:1)).

## 0) Самые важные уточнения (до 7)

Даже без ответов ниже есть рабочий план «по умолчанию», но точность рекомендаций по железу и эхоподавлению сильно зависит от деталей.

1) Какая модель Raspberry Pi (3B / 4B / 5) и какая ОС (Raspberry Pi OS 32/64)?
2) Что именно от «Станции Мини» у тебя есть и в каком виде: только динамик, или плата усилителя тоже доступна/снята?
3) Микрофон: уже есть USB, или планируешь I2S MEMS / ReSpeaker (2-Mic/4-Mic)?
4) Насколько близко физически будут динамик и микрофон (в одном корпусе/на столе/разнесены)?
5) Нужна ли активация/прерывание ответа голосом (barge-in) или можно «глушить микрофон» на время TTS?
6) Важнее цена или качество/латентность (например, «не дороже X ₽/мес»)?
7) География/доступность: есть ли ограничения по провайдерам (например, лучше Яндекс, либо наоборот нужен OpenAI)?

План по умолчанию ниже предполагает: Raspberry Pi 3B/4B, интернет всегда, микрофон USB или ReSpeaker, и допустимо подавление микрофона на время TTS как безопасный дефолт, а barge-in добавляется позже.

### Зафиксированный профиль (по твоим ответам)

- Raspberry Pi 3B (2 GB)
- Используем **USB-микрофон**
- Динамик в том же корпусе (высокий риск акустического эха)
- Нужен **stop-word** (барж-ин только для команды «стоп/отмена», не обязательно для полного диалога)
- Приоритет: **стоимость важнее**, провайдеры доступны любые

## 1) Целевая архитектура пайплайна (провайдер-агностичная)

### 1.1 Компоненты (потоки данных)

1) Захват аудио (локально): непрерывный поток PCM16 16 kHz mono.
2) VAD (локально): маркируем кадры как speech/non-speech, даём метрики качества.
3) Wake (локально): быстрый и дешёвый детектор «олег» с логами «кандидат/принят/отклонён».
4) Запись команды (локально): буферизация pre-roll + post-roll, таймауты начала/конца.
5) ASR (облако): near-real-time (короткая фраза 1–10 секунд) с ретраями и таймаутами.
6) NLU/LLM (облако): диалоговый контекст, safety-ограничения, инструменты (опционально).
7) TTS (облако): генерация WAV/PCM + кэширование повторов.
8) Воспроизведение (локально): стабильный вывод, управление громкостью, возможность stop (для barge-in).

Ключевой принцип: «аудио-нить» никогда не блокируется сетью. Сеть работает в отдельном asyncio-контуре; state-machine отдаёт «готовый аудио-буфер команды» в очередь.

### 1.2 Чёткие интерфейсы (чтобы менять провайдеров)

У тебя уже есть удачное разделение по интерфейсам провайдеров: [`assistant/cloud_interfaces.py`](assistant/cloud_interfaces.py:1).

Цель довести до:

- STT интерфейс поддерживает два режима: пакетный (WAV bytes) и потоковый (опционально, если провайдер поддерживает).
- TTS интерфейс умеет возвращать либо WAV bytes, либо поток chunks (для меньшей задержки).
- LLM интерфейс принимает нормализованные messages и возвращает текст + usage/raw.

Оркестратор (pipeline orchestrator) принимает зависимостями реализации интерфейсов, а не создаёт их внутри.

### 1.3 Что локально, что в облаке — и почему

Оставить локально:

- захват/плейбек аудио: надёжность, детерминированность, минимум задержки;
- VAD: дешёвый, уменьшает объём данных для STT и снижает ложные срабатывания;
- wake: критично по latency и устойчивости (даже при сетевых лаггах ассистент должен «просыпаться»);
- запись команды и state-machine: контролируемость, логирование, воспроизводимость багов.

В облако:

- ASR: качество на русском и в шуме лучше, обновления моделей без твоего участия;
- LLM: качество диалога/обобщения, инструменты;
- TTS: естественность и голоса (особенно русские), меньше возни с локальными голосами.

Отдельный важный нюанс под твой профиль (USB mic + динамик в одном корпусе):

- wake и «стоп-слово» должны быть локальными, но на время TTS **нужно управлять входом**:
  - «безопасный дефолт»: глушить микрофон во время TTS (у тебя уже есть через `SPEAKING_EVENT`, см. [`assistant/main_cloud.py`](assistant/main_cloud.py:88));
  - «нужен stop-word»: включаем микрофон во время TTS, но в режиме **жёсткого детекта** (ограниченная грамматика + строгий порог/энергия + VAD), чтобы не ловить собственный TTS.
  - если захочешь полноценный barge-in (перебивать ответ любой фразой) — тогда почти неизбежен AEC (см. раздел 2.5).

## 1.4 Провайдеры (варианты 2–3) и рекомендация

Ниже — практичные варианты с фокусом на русском, latency и простоту.

### Вариант A (лучший дефолт): OpenAI (ASR + LLM + TTS)

Где в проекте: уже есть [`assistant/cloud_openai.py`](assistant/cloud_openai.py:1).

Плюсы:

- очень быстрое внедрение (у тебя уже готово);
- хорошее качество ASR/LLM/TTS, единый ключ, единая сеть;
- предсказуемые API и ретраи.

Минусы:

- стоимость может быть выше «локальных» провайдеров;
- зависимость от внешнего сервиса.

Когда выбирать: «хочу максимум качества и минимум интеграционных страданий».

### Вариант B (часто лучший в РФ по стабильности и цене): Yandex SpeechKit + (LLM отдельно)

Конфигурация: STT+TTS Яндекс, LLM — OpenAI или другой.

Плюсы:

- сильные русские голоса и стабильный STT на русском;
- в РФ часто меньше latency/проблем с доступностью;
- гибкие тарифы.

Минусы:

- два провайдера (сложнее эксплуатация, два ключа/лимита);
- интеграция придётся добавить (новые файлы провайдера).

Когда выбирать: «важна русская TTS и стабильность в РФ».

### Вариант C (универсальный корпоративный): Azure Speech + Azure OpenAI / OpenAI

Плюсы:

- enterprise-инфраструктура, хорошие SLA;
- качественный Speech stack.

Минусы:

- сложнее конфигурация, чаще больше бюрократии;
- иногда выше latency.

Когда выбирать: «нужна корпоративная эксплуатация/учётки/аудит».

Рекомендация:

- дефолт: OpenAI end-to-end для быстрого выхода на качество;
- «бюджетно/просто (и хорошо по-русски)»: Yandex STT+TTS + LLM по ситуации.

### Конкретные «дефолты» под Raspberry Pi 3B + стоимость

Твоя архитектура уже позволяет оставить тяжёлое в облаке, поэтому узкое место — не CPU, а **стоимость и задержка сети**.

Рекомендованные пресеты:

1) **Бюджетный/практичный (рекомендую начать с этого)**
   - STT: Yandex SpeechKit (русский, устойчивость)
   - TTS: Yandex SpeechKit (русские голоса)
   - LLM: OpenAI `gpt-4o-mini` (как дефолт) или другой недорогой LLM
   - Почему: самые «заметные пользователю» компоненты на русском (STT/TTS) часто лучше/дешевле локально по региону, а LLM можно менять.

2) **Самый простой в интеграции (у тебя уже почти готово)**
   - STT+LLM+TTS: OpenAI (см. [`assistant/cloud_openai.py`](assistant/cloud_openai.py:1))
   - Почему: меньше движущихся частей, быстрее довести до стабильного состояния.

3) **Минимальная стоимость при приемлемом качестве**
   - STT: Yandex SpeechKit (или OpenAI STT — сравним по цене/качеству на твоих данных)
   - LLM: более дешёвый провайдер/модель (подберём после метрик)
   - TTS: Yandex SpeechKit
   - Почему: LLM обычно основной «счётчик» расходов; его проще всего оптимизировать (ограничение контекста, короткие ответы, сжатие истории).

Для выбора окончательно: после внедрения метрик (latency + стоимость/сутки) ты сможешь принять решение по цифрам, а не «на ощущениях».

## 2) Железо и аудио-тракт (динамик от Станции Мини)

### 2.1 Ключевой факт

Динамик нельзя подключать напрямую к Raspberry Pi. Нужны:

- ЦАП (DAC) или USB-аудио (чтобы получить линейный/цифровой аудиосигнал),
- и усилитель (класс D) под нужный импеданс/мощность.

### 2.2 Варианты подключения (по простоте)

Вариант 1 (самый простой и надёжный): USB sound card + отдельный усилитель

- USB звуковая карта даёт line-out/наушники.
- Дальше — любой маленький усилитель класса D (на 5V/12V) на нужную мощность.
- Плюсы: минимум возни с драйверами, работает почти везде.
- Минусы: чуть больше проводов, качество зависит от USB-карты.

Вариант 2 (рекомендуемый для аккуратной сборки): I2S DAC+AMP (HAT или модуль)

- Raspberry Pi выдаёт I2S, модуль типа MAX98357A (I2S → усиленный выход на динамик).
- Плюсы: меньше шума/наводок, компактно.
- Минусы: нужно настроить device tree overlay, аккуратная разводка питания.

Вариант 3: готовый аудио-HAT (DAC + amp) под динамик

- Плюсы: «поставил и забыл».
- Минусы: цена.

### 2.3 На что смотреть по динамику

Без точных данных по динамику от Станции Мини безопасный дефолт: считать, что динамик 4 Ом, 3–5 Вт. Значит:

- усилитель должен стабильно работать с 4 Ом;
- питание усилителя — отдельное/хорошо фильтрованное, иначе будет фон;
- общий GND, короткие провода к динамику.

### 2.4 Если ты решишь «новый динамик по line-out / Bluetooth»

- **Line-out** (USB sound card → усилитель → динамик): лучший баланс «дёшево/надёжно/мало задержки».
- **Bluetooth-колонка**: работать будет, но часто:
  - выше задержка (неприятно для ассистента);
  - нестабильное переподключение;
  - сложнее AEC/stop-word (эхо становится менее предсказуемым).
  Поэтому BT — только если критично убрать провода.

### 2.4 Шумы/питание/земля

- Raspberry Pi и усилитель лучше питать от качественного БП с запасом по току.
- Если слышен писк/фон: чаще виноват общий провод и DC-DC, лечится фильтрами/разводкой/отдельным питанием усилителя.

## 2.5 Микрофон и эхоподавление

### Микрофон: варианты

USB-микрофон:

- лучший «plug & play»;
- проще дебажить и менять.

I2S MEMS / ReSpeaker:

- выше шанс получить приемлемый звук в одном корпусе;
- некоторые платы дают beamforming/AGC.

### Эхо (AEC)

Если микрофон рядом с динамиком, AEC становится критичным, иначе TTS будет триггерить wake.

Практичный дефолт на старте (и он уже есть у тебя): подавлять микрофон во время TTS через флаг (см. [`assistant/config.py`](assistant/config.py:49) и использование `SPEAKING_EVENT` в [`assistant/main_cloud.py`](assistant/main_cloud.py:88)).

Под твой профиль (нужно только stop-word):

- сначала делаем **best-effort stop-word без AEC**:
  - локальная детекция «стоп/отмена/хватит» с очень ограниченным словарём;
  - строгие пороги по VAD/энергии;
  - cooldown и защита от самосрабатывания на TTS.
- если окажется, что в твоём корпусе TTS часто «пробивает» и стоп-слово нестабильно — добавляем AEC.

AEC варианты:

1) системный echo-cancel (PipeWire/PulseAudio)
2) программный AEC (webrtc-audio-processing) перед VAD/wake

## 2.6 ALSA / PulseAudio / PipeWire на Raspberry Pi

Дефолтная рекомендация:

- если Raspberry Pi OS свежая и стоит PipeWire: использовать PipeWire (меньше «магии» для приложений, удобнее echo-cancel);
- иначе PulseAudio подойдёт; важнее стабильность устройств и фиксированные device ids.

Обязательные практики:

- фиксировать устройства по имени/порту, а не по «карте 0/1» (они меняются);
- выставить sample-rate 48000 для системы, а внутри ассистента держать 16000 (ресемплинг делается один раз);
- проверять underflow/overflow по логам.

## 3) Код: довести до «почти идеала» (пошагово)

Ниже — целевой список изменений. Реализацию будем вносить постепенно через отдельные коммиты/патчи, чтобы не ломать работающий пайплайн.

### 3.1 Структура проекта

Текущая структура уже неплохая. Цель: отделить «ядро пайплайна» от «провайдеров» и от «адаптеров железа».

Предлагаемые папки (без фанатизма):

- assistant/core: state-machine, события, доменные типы
- assistant/providers: openai, yandex, azure (по желанию)
- assistant/audio: захват/плейбек/ресемплинг/AEC hooks
- assistant/ops: systemd helpers, healthcheck

### 3.2 Конфиг

Оставляем env как source of truth (как сейчас в [`assistant/config.py`](assistant/config.py:1)), но добавляем:

- опциональный config-файл (yaml/toml) для удобства на RPi, с приоритетом env > file > defaults;
- валидацию конфигурации при старте (например, ключи/таймауты/модели);
- единый вывод конфигурации в логах (без секретов).

### 3.3 Надёжность облака

- явные таймауты (connect/read/total),
- ретраи с backoff и jitter на 429/5xx,
- лимиты параллелизма (например, не больше 1 STT/LLM/TTS одновременно),
- корректная отмена при shutdown.

### 3.4 Оркестратор

Цель: аудио state-machine (wake+record) остаётся синхронной и работает в отдельном thread, но отдаёт результат в asyncio очередь.

Отдельные корутины:

- worker_stt: WAV → текст
- worker_llm: текст → ответ
- worker_tts: ответ → WAV
- player: WAV → устройство

Это даст:

- возможность barge-in (остановить player, сбросить очереди),
- стабильное поведение при лаге сети,
- измерение latency по стадиям.

### 3.5 Wake/VAD: калибровка и расширенное логирование

Цель: автоматом подобрать WAKE_MATCH_THRESHOLD и WAKE_MIN_SPEECH_RATIO для конкретного микрофона/шума.

Идея калибровки:

- собрать 20–30 примеров: фон (без речи) + произнесение wake в разных громкостях;
- логировать для каждого кандидата: score, speech_ratio, длину, уровень энергии, решение (принят/отклонён) и причину;
- подобрать порог так, чтобы false accept на фоне был ~0, а false reject на wake был минимальным.

Это можно оформить как отдельную команду/скрипт, сохраняющий отчёт и предлагающий значения env.

### 3.6 Edge-cases

- «олегкакдела»: уже учтено в пайплайне; надо закрепить тестами.
- быстрые реплики/паузы: адаптивный end-of-speech (max_silence зависит от VAD confidence).
- повторный wake во время ответа: либо cooldown, либо barge-in.
- защита от самотриггера TTS: дефолтно suppress mic during TTS; позже AEC.
- отмена: слово «отмена/стоп» как отдельный быстрый локальный детектор (опционально).

### 3.7 Тесты

- unit: postprocess, таймауты, логика state-machine (у тебя уже есть базовые тесты в [`assistant/tests/test_postprocess.py`](assistant/tests/test_postprocess.py:1) и [`assistant/tests/test_timeouts.py`](assistant/tests/test_timeouts.py:1)).
- integration: мок провайдеров STT/LLM/TTS, проверка очередей/отмен.
- audio fixtures: набор wav с реальными кейсами (wake отдельно, wake+команда слитно, шум, TTS leakage).
- golden tests: ожидаемые тексты/решения stop reason.

## 4) Эксплуатация на Raspberry Pi

У тебя уже есть systemd unit: [`deploy/assistant.service`](deploy/assistant.service:1) и env-шаблон: [`deploy/assistant.env.example`](deploy/assistant.env.example:1).

Целевой стандарт:

- systemd service с Restart=always, ограничением ресурсов и отдельным пользователем;
- секреты только в env-файле с правами 0600;
- логи в journald + ротация;
- healthcheck (опционально): простой HTTP /metrics или хотя бы периодический «heartbeat» в лог.

Мини-чеклист диагностики (будет вынесен в README отдельным разделом):

- перечисление устройств захвата/вывода,
- запись 5 секунд и прослушивание,
- тест проигрывания wav,
- end-to-end тест: wake → команда → ответ → TTS.
